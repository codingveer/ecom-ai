# SKU Tagging Admin App Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a person correct a SKU's category/tags/attributes and set a manual relevance nudge, with both lexical and semantic search reflecting the change immediately — fixing the root cause of poor "semantic" results (randomly-assigned seed tags), not the ranking math.

**Architecture:** Three new tool contracts (`catalogue.admin.list/get/update`, `allowed_agents: ["admin"]`) route through the existing tool gateway to three new routes in `packages/services` (which already owns D1, Workers AI, and Vectorize). `packages/app` gets three thin proxy routes built on the existing `Kernel` class (same pattern `/outcome` already uses, agent identity `"admin"`) plus one new static page, `admin.html`. No new Worker, no new bindings — `packages/services` stays unreachable except via service binding, exactly as today; the only browser-facing surface is `packages/app`.

**Tech Stack:** Existing Hono services/app/tools Workers, D1, Workers AI (`@cf/baai/bge-base-en-v1.5`), Vectorize — all already wired. No new npm dependencies. Admin UI is vanilla HTML/JS, no framework, consistent with `shop.html`.

**Reference design doc:** `docs/superpowers/specs/2026-09-17-sku-admin-design.md`

## Global Constraints

- `relevance_boost` defaults to 0 for every row via the schema's `DEFAULT 0` — ranking/search behavior for every currently-seeded product must be byte-for-byte identical to today until an admin explicitly sets a non-zero value. `npm run smoke` must pass unmodified throughout.
- No new Worker and no new `wrangler.jsonc` bindings anywhere. The only new surface is: 3 tool contracts, 3 `services` routes, 3 `app` routes, 1 static page.
- `packages/services` remains `workers_dev: false` — its new admin routes are reachable only via the `tools` service binding (or a local `wrangler dev` port), never directly from a browser once deployed. The only browser-facing surface is `packages/app`.
- No auth on the admin routes or page — confirmed acceptable, internal prototype tool, matches this demo's existing security posture.
- One SKU editable at a time. No bulk-edit endpoint or UI in this plan.
- `style_tags` stays the existing comma-joined `TEXT` column — admin input is free text, not constrained to the original 8-word `STYLES` seed list.
- `ToolContract.input_schema` (`packages/tools/src/types.ts`) has no enum support — same constraint every existing contract lives with.

```ts
/** Same template scripts/gen-seed.ts's describeProduct uses at seed time - duplicated here,
 * not imported, because scripts/ runs under Node for codegen and this Worker runs on the
 * Workers runtime. Keeps a retagged SKU's embedded text consistent with a freshly-seeded one. */
function describeProduct(p: { title: string; category: string; brand: string; colour: string; material: string; cut: string; styles: string[] }): string {
  const cutPhrase = p.cut === 'runs_small' ? 'a snug, true-to-body cut'
    : p.cut === 'runs_large' ? 'a relaxed, roomy cut'
    : 'a true-to-size cut';
  const tagPhrase = p.styles.join(', ');
  const article = /^[aeiou]/i.test(p.colour) ? 'An' : 'A';
  return `${article} ${p.colour} ${p.material} ${p.title.toLowerCase()} by ${p.brand}, ${cutPhrase}, `
    + `from the ${p.category} range, tagged ${tagPhrase}.`;
}

const ADMIN_EDITABLE_FIELDS = [
  'category', 'department', 'brand', 'colour', 'material', 'cut', 'style_tags', 'price_tier', 'relevance_boost',
] as const;

app.post('/admin/products/:sku', async c => {
  const sku = c.req.param('sku');
  const existing = await c.env.DB.prepare(`SELECT * FROM products WHERE sku = ?`).bind(sku).first<any>();
  if (!existing) return c.json({ error: 'sku_not_found' }, 404);

  const body = await c.req.json<any>();
  const next = { ...existing };
  for (const field of ADMIN_EDITABLE_FIELDS) {
    if (body[field] !== undefined) next[field] = field === 'relevance_boost' ? Number(body[field]) : String(body[field]);
  }

  const description = describeProduct({
    title: next.title, category: next.category, brand: next.brand, colour: next.colour,
    material: next.material, cut: next.cut,
    styles: String(next.style_tags).split(',').map((s: string) => s.trim()).filter(Boolean),
  });

  await c.env.DB.prepare(`
    UPDATE products SET category=?, department=?, brand=?, colour=?, material=?, cut=?,
      style_tags=?, price_tier=?, relevance_boost=?, description=? WHERE sku=?`)
    .bind(next.category, next.department, next.brand, next.colour, next.material, next.cut,
      next.style_tags, next.price_tier, next.relevance_boost, description, sku).run();

  let reindexed = false;
  let degraded_reason: string | undefined;
  try {
    const embedded = await c.env.AI.run(EMBED_MODEL as any, { text: [description] }) as any;
    await c.env.VECTORS.upsert([{ id: sku, values: embedded.data[0], metadata: { category: next.category } }]);
    reindexed = true;
  } catch (e) {
    degraded_reason = e instanceof Error ? e.message : 'reindex failed';
  }

  return c.json({ sku, updated: true, reindexed, ...(degraded_reason ? { degraded_reason } : {}) });
});
```

Only the nine whitelisted fields are ever written — the request body can never inject an arbitrary column name into the `UPDATE` statement, since the column list is static text and `ADMIN_EDITABLE_FIELDS` only controls which *values* are merged in before that fixed statement runs.
